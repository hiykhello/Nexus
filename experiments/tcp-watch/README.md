# TCP 输出代次观察成本

实验构建入口尚待迁入当前工作区。程序对 IPv4 和 IPv6 分别保留指定数量的不同四元组令牌，然后各执行 20,000 次临时令牌登记、20,000 次持有同一四元组令牌时的登记和 20,000 次 open/abort。输出为平均纳秒；后者包含连接创建和释放，并非纯观察表扫描。保留的四元组与 open 的四元组不同，因此模拟无关积压。此基准不包含包解析、队列、socket、线程竞争或实际流量，也不测尾延迟。

2026-10-29，本机 i9-13900H、GCC 16.2.1、xmake release，共享令牌改造前的单次结果：

| 族 | 保留令牌 | watch ns/次 | open/abort ns/次 |
| --- | ---: | ---: | ---: |
| IPv4 | 0 | 24 | 282 |
| IPv4 | 64 | 31 | 953 |
| IPv4 | 256 | 206 | 3384 |
| IPv4 | 1024 | 551 | 11899 |
| IPv6 | 0 | 18 | 373 |
| IPv6 | 64 | 35 | 1087 |
| IPv6 | 256 | 109 | 3165 |
| IPv6 | 1024 | 573 | 13071 |

结果只展示此机器、一次运行的数量级；频率变化和其他负载会影响结果。改造前每次 watch 创建一个控制块；改造后同一四元组的在途包共享有效令牌，新流打开时使旧令牌失效。watch 线性查找并清理过期观察项；open 线性扫描观察项，锁定仍存活的弱引用。该基准表明积压时成本上升，但不足以判断实际吞吐或尾延迟，也没有比较替代实现。

## 保留量与约束

默认 LinuxTunDirect 中，两个 TCP 内部输出队列各最多 64 个，外部输出队列最多 64 个，交换器和设备泵各最多持有一个，两个 TCP 引擎各最多保留一个待发包。因此驱动自身最多同时保留 196 个输出 TCP 包的令牌；队列字节限制可能进一步收紧这个上界。一次登记过程中还可能有一个临时令牌。自定义队列参数相应改变上界；这不是连接数限制。

观察表保存弱引用，只有后续 watch 或成功 open 才清理过期项；因此最后一个包释放后，弱引用和控制块可能保留到下次清理或表销毁。vector 容量也不会随清理自动缩小，实际分配字节数取决于标准库及分配器。上述数量上界只适用于驱动控制全部输出、遵守单 owner 约束且没有外部额外观察者的场景。公开 `watch` 和 `receive_packet` 的调用方可以无限保留令牌或包，观察表不提供独立的硬上限。

按四元组共享令牌减少同一流多包积压的分配和观察数，但不同四元组仍可无限增长；为公开接口设置硬上限需要定义耗尽时的丢包、背压及异常恢复语义。哈希索引还需处理对端可控键、碰撞、异常回滚和过期清理。当前没有实际负载数据证明整体吞吐或尾延迟收益；使用者应遵守所有权约束，并在最终投递及每次重试前验证元数据。
