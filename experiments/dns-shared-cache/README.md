## Hazard pointer 生命周期探针

```sh
bash experiments/dns-shared-cache/run_hazard.sh /tmp/nexus-xenium
```

探针在一个线程保留查找迭代器，另一个线程删除该节点、反复触发退役扫描并退出；验证节点直到读者释放前都未析构。该次运行在释放迭代器时节点仍未析构，随后另一个线程继续制造退役并触发扫描，节点才析构。独立进程重复 20 次均通过。这验证的是固定上游版本和该具体时序，不代表空闲时会及时回收，也不证明任何总内存上限。

同一表达式中的 `get_or_emplace(...).second && erase(...)` 保留了插入结果的临时迭代器，随后删除会耗尽默认 3 个线程局部槽并抛出 `bad_hazard_pointer_alloc`；将两个操作放在不同完整表达式后，探针中的操作正常。生产实现必须明确 guard/临时对象作用域、最大嵌套槽需求与异常处理，不能把默认槽数当作任意组合操作的安全上限。固定版本中，线程退出会扫描并转移仍被保护的退役节点，之后需要其他扫描接管；停止和内存预算设计必须考虑闲置期间及读者挂起时的保留。探针没有测试分配失败、线程迁移、竞争检测或全部停机场景。

## 固定投放速率的混合读写

> 此组实验的构建及运行入口待迁入当前工作区。

脚本将 8 个读者和一个写者分别绑到给定 CPU，所有读者各投放 50000 次/s，写者投放 1000 或 10000 次/s，各场景运行 3 秒。每个请求到指定时间才尝试，若调度或前一操作耽误整个时槽则跳过，CSV 分别记录总投放、完成和跳过数量；不是无限排队或追赶突发。读服务时间每 100 个时槽采样，写服务时间每次采样，同时记录服务开始距计划时间的偏差。程序在等待期间让出 CPU，并在请求时检查答复一致性。每 worker 模式的写者将同一个结果依次发布到每个本地缓存，复制期间没有跨缓存原子性；这表示一次广播，并不模拟其实际重复上游请求。

## 有序索引与模块候选

## 真实代理回环比较

> 此组实验的构建及运行入口待迁入当前工作区。

三个 fixture 使用同一 SOCKS 代理代码，分别选择每 worker 缓存、共享锁和模块快照，未启用每次缓存访问的测试钩子。Python 同一事件循环承担固定速率客户端、UDP DNS 对端及回环目标；每时槽投放 8 个独立连接，64 会话配额下客户端最多持有 48 项。固定 DNS 数据为 A 回环地址和带 SOA 的 AAAA NODATA。热点与 64 键均匀场景先预热 32 轮；唯一名称场景均返回 NXDOMAIN；短 TTL 场景以 64 名称循环、同批次访问同一键，产生到期后的并发重查，**不是后台乐观刷新**。每轮 DNS 答复和投放计划相同，但不同缓存的实际上游请求数可能不同。输出逐场景 JSON，记录计划、完成、失败、漏投、上游 DNS 请求、成功请求的计划到完成和服务时间分位数、代理 RSS 高水位、CPU tick 与停止时间；未完成和跳过的请求不计入延迟分位数。

`proxy-{1,2}.jsonl` 为改动槽初始化前的 8 worker、800 请求/s、8 秒正反序两轮；每场均完成 6400/6400，无失败或漏投。计划到完成 p99：热点每 worker 3.79–3.82 ms、共享锁 3.92–4.02 ms、快照 3.78–3.83 ms；均匀分别为 3.79–3.91、3.84–3.98、3.81–3.86 ms。均匀模式每 worker 在测量期间仍有 9–10 次 A 和 AAAA 冷查询，共享模式为零；短 TTL 的具体上游次数和其他场景见原始数据。初始化优化后 1600 请求/s 的正序 `proxy-lazy-1.jsonl` 全部完成 12800/12800；反序 `proxy-lazy-2.jsonl` 的短 TTL per-worker 场景出现 269 个失败、12052 个并发上限跳过，后续逐步恢复，下一场预热超时中止，原因未确定。随后的短 TTL 三模式单独重跑均成功，不能抹去该失败。

## 多入站容量轨迹

> 此组实验的构建及运行入口待迁入当前工作区。

两个入站各顺序访问 256 个域名，先预热一轮，再重复两轮共 1024 次访问；TTL 保持有效。完全重叠时，每入站 256 项缓存共保存 512 条，共享 256 项快照保存 256 条，两者都全部命中。不重叠时，每入站缓存和共享 512 项锁缓存都全部命中，而共享 256 项快照全部未命中：每次补入的键都淘汰了随后需要的键。`AddressCache` 的共享快照目前最多 256 项，512 项使用现有共享锁模式。

这是构造出的最坏顺序，用来展示容量合并的语义后果；它没有模拟 DNS 往返、并发、TTL 变化或衡量延迟，也不能代表所有入站的命中率。简单增加全局容量能容纳该轨迹，但读写成本、热点竞争、最坏历史版本内存和不同入站容量隔离仍需比较。不能直接把每入站各 256 项改为全进程共 256 项。

同一程序还检查总容量相等时的入站隔离：A 和 B 在相同解析视图中各填入 256 个不同名称，A 的期限为 3600 秒，B 为 600 秒；随后 A 发布 256 个期限为 7200 秒的新名称，整个轨迹的时钟不推进，全部答复都仍有效。两份各 256 项缓存保留 A 的 256 个新名称和 B 的 256 个名称；单份 512 项共享锁或完整语义分页缓存都淘汰 B 的全部名称，保留 A 的 512 个名称。这是由按最早到期淘汰和构造的访问顺序产生的特例，不代表实际平均命中率，但说明仅把容量加总也不能保持原有的入站隔离。

`nexus-dns-group-membership-experiment` 是单线程抽象模型：每个入站维护独立配额和淘汰顺序，兼容视图、名称及类型完全相同时，入站首次未命中可接纳其他入站仍持有的新鲜答复。同键的新答复更新所有已接纳该键的入站，零 TTL 及 owner 清空使相关引用失效；入站退出只释放自己的引用。两组各 256 项完全重叠时为 512 个引用、256 份答复；上述公平性轨迹保留 B 的 256 项。模型还检查不同视图、跨入站更新、期限、最后引用释放、17×256 容量及固定随机混合操作。

> 此组实验的构建及运行入口待迁入当前工作区。

这个模型使用 `shared_ptr`、`std::map` 和线性扫描，未实现查询/刷新令牌、stale、并发、分配失败或 reader 生命周期；它只用于确认一种语义选择，不是生产数据结构，也不能用于推断性能。首次跨入站命中需要修改该入站成员索引；更新同键需要原子地更新所有已接纳该键的索引，以免不同入站读到不同的新旧版本。后续需明确公共 clear 的范围、预算耗尽和分配失败时的行为，并以完整缓存语义和真实流量验证。

`group_snapshot.hpp` 把该选择放入不可变根和分页成员索引。每个根包含最多 17 个入站索引，索引各自最多 256 项；节点在同一根的多个索引间共享，读者只保护一个根，首次跨入站未命中才进入写者慢路径接纳引用。原型现支持正负答复、TTL、stale、刷新与查询令牌和共同 clear，单入站与正式锁缓存进行了 30000 步混合差分。`group_snapshot_test.cpp` 还覆盖 4352 个不重叠成员、重叠答复、跨组更新与刷新去重、淘汰后旧刷新、接近时钟上限、历史根以及 8 读者与发布/清空交错；故障目标对发布、跨多组更新并淘汰、接纳、构造和无分配 clear 逐位置注入 `bad_alloc`，并在隔离 TSan/ASan/UBSan 下运行（系统预编译库未插桩）。跨组回滚测试发现旧实现的临时节点所有权在异常时不安全，现已修正并重跑。该原型尚无全局字节预算、跨 executor 真实任务或生产生命周期，仍需更多混合故障、压力和真实路径验证。

不同执行器采集的单调时间可能逆序抵达：慢路径现在把较晚的观测时间发布到根，防止已经看到 stale/过期的答复因另一个较早的采样再次变成新鲜。新增跨组时间逆序与 stale/负答复接纳和失效的分配故障回滚测试，release 与隔离 TSan、ASan/UBSan 均通过。新鲜命中仍只读取受保护根，返回 TTL 根据当次时间和已发布时间保守计算；该设计不提供系统时间回拨检测。

成员索引原型增加可选的快照计费预算：预留读者槽和根池、当前/旧根引用的节点、索引、页，以及构造中的写入副本均计入；答复节点按已压缩容器容量及其对象估算，页和索引按对象大小计数。写入因额度不足无法安全发布时，原型关闭所有缓存读取并清除待处理登记，直到调用共同 clear；跨入站接纳额度不足仅将该次当作未命中。启用有限预算时，注册前台查询或写入发生 `bad_alloc`、以及前台登记耗尽时也关闭缓存，避免旧结果在新应答无法登记/发布后继续命中。clear 和恢复会改变读取 epoch，使跨越禁用/恢复的读者不能返回旧根；释放的历史根在下次分配前回收。测试覆盖两份不同历史、真实线程固定旧根、预算恰好耗尽、全局登记上限、分配故障与清空后恢复，并验证计费峰值不越过设定额度；release、隔离 TSan 和 ASan/UBSan 通过。

这个预算只约束模型计费的快照存储，不是 RSS 或进程总内存上限：它不含分配器元数据、待处理登记及任务、调用方传入/取出的答复缓冲区、临时参数副本、网络消息或其他模块。预算可能在替换时需要同时容纳新旧版本，容量设置过低会触发全局旁路并增加查询；示例未选择生产默认值或自动恢复策略。`begin_query` 调用前的参数构造若失败也不在这个模型的保护范围内，真正接入时必须让解析 owner 覆盖该边界，并验证故障期间上游行为和缓存可用性。这个设计尚未接入生产。

## 分页快照原型

`paged_snapshot.hpp` 仅用于探索扩大共享容量：不可变根保存排序页，页最多 32 项，查询时保护根并在根和页内分别二分查找；单写者复制根指针和改变的页。它只实现正答复、有限 TTL、查询令牌和容量淘汰，没有负答复、stale/刷新、clear 或生产生命周期，不能替代 `AddressCache`。节点的计数原子用于实验，会影响写路径。

> 此组实验的构建及运行入口待迁入当前工作区。

连续分裂后让短 TTL 项过期的构造轨迹曾令 481 条记录各占一页；在本机一个页为 288 字节，单这些页就约 135 KiB。现每次发布合并相邻且总数不超过 32 的页，同一轨迹剩 16 页；测试逐轮检查相邻页总数大于 32、所有保留条目可读。由此在最多 512 项的已发布根中最多有 31 页；一次构造中的分裂可能暂时增加一页。根从预留 512 个指针改为预留 32 个，并为 `W` 个读者预留 `W+2` 个根。慢读者可以保留不同历史根和页，节点数仍随读者数增加；完整历史数据以及页和分配器的最坏峰值不能用单个当前根估计。原型接受的答复容器可以携带过量预留容量，因此这里没有声称严格字节上限。

正答复 30000 次差分、512 项容量与过期、8 读者竞争、4 个不同历史版本、合并时旧读者持页及释放后回收，以及 8 读者与反复过期合并交错均已验证。逐位置注入普通和对齐分配失败，分裂、淘汰、过期和需复制左页的合并分别覆盖 10、11、10 和 10 次失败，失败后旧版本可读且可重试。独立临时构建的 TSan 和 ASan/UBSan 覆盖 DNS 模块和测试及一个插桩的 `std`，系统预编译标准库和网络栈未插桩。这些测试不是完整安全审查。

`groups-paged-smoke.csv` 是合并前的 1 秒功能试运行，运行时另一个项目有较高 CPU 负载；`groups-paged-merged-smoke.csv` 是合并后的试运行，同样存在其他负载和遗漏。两者仅用于确认八种模式能返回正确结果，不能用于性能比较。

`groups-paged-{1,2}.csv` 是合并后每读者每秒投放 50000 读、正反序各一轮的三模式对照，方法与前述 512 项实验相同。仅举两种负载的服务时间 p99，单位纳秒，取两轮的范围：

| 不重叠、热键、1000 写/s | 读 | 866–1035 | 913–924 | 1537–1739 |

分页写入在各个样本中较低，但部分读场景较慢；各场数据、RSS 和完整调度偏差见 CSV。每场计划 120 万读，最多跳过 117630 次；写分别计划 3000 或 30000 次，最多跳过 82/3000 或 124/30000 次。读延迟仅对每 100 个投放槽采样，跳过的操作不进入分位数。主机仍运行桌面和其他项目任务，环境快照见 `groups-paged-environment.txt`，没有逐次隔离系统负载；固定 CPU 含 P/E 核，频率未隔离，单场仅 3 秒。因此不能把差异归因于缓存结构或推断生产性能。

另将每读者投放降至 20000 读/s 重复正反序，见 `groups-paged-low-{1,2}.csv`。每场计划 480000 读；最差分页场次跳过 77378 次读和 4607/30000 次写，约为各自投放的 16.1% 和 15.4%。该轮的环境快照 `groups-paged-low-environment.txt` 记录了其他项目的编译活动，但采样不足以确定哪一项造成漏投。降低读投放并未解决调度干扰，也不能将漏投排除后比较 p99 视为等负载。

`memory-paged.csv` 比较同为 512 项的实验有序快照和分页原型，每种独立进程重复三次，按 `mallinfo2` 堆与 mmap 增量和 `smaps_rollup` RSS 增量计量，未固定历史版本。257 个读者、空缓存时，有序版分配 1097968 字节、RSS 增量 1167360 字节；分页版分别为 95360 和 163840 字节。257 个读者、512 条答复时，分配分别为 1327520 和 331344 字节，RSS 增量分别为 1503232–1519616 和 430080–475136 字节。实验有序版预初始化完整数组，正式 256 项模块的按需初始化与它不同；RSS 还包含装页、运行库及测量本身。这不是停滞读者历史峰值，也不是跨进程或实际代理负载。

`memory-paged-history.csv` 在独立进程中构造 4、8 或 16 个停滞读者：每个读者固定一个版本后重写全部 512 条答复，最后取样，并验证此前各版本仍可读。16 读者时，有序版和分页版在全部历史固定后的分配增量分别为 4394080 和 4407584 字节；释放读者并再写一次以触发回收后分别降为 335664 和 275904 字节。对应 RSS 增量仍约 4.46–4.50 MB，分配器未立即归还内存。每种条件重复三次；取样发生在完整历史固定后，未追踪更新过程中的瞬时最大值，缓存输入是同尺寸的小答复，也没有测 257 个真实慢线程。这说明分页减少空闲根的成本，并不消除历史答复随读者数增长的风险。

## 分页完整语义实验

`paged_semantic.hpp` 在另一个实验版本中实现正负答复、TTL 0、stale 窗口、查询与刷新令牌、失效及清空；输入保存前收缩超额预留容量。正答复原型仍单独保留，前述性能和内存测量不适用于这个版本。stale 查询和刷新资格检查会取得写锁并构造新根；后台任务配额、生命周期与跨入站共享尚未接入，不能当作正式缓存。

#### 前台合并与不足一秒 TTL 的独立实验

`group_singleflight.hpp` 和 `group_coalesced_resolve.hpp` 尚未接入生产；它们已用于下述测试版代理及新的性能对照夹具。一份不可变配置拥有 `FlightGroup`；每个 executor 的 owner 借用它，查询由 group 的 `unique_ptr` 独占，等待节点由调用操作拥有并以侵入链登记。最后等待者离开后，网络任务排空前保留名额；完成后慢等待者仍保留名额和答复，任务及等待者全部结束才释放。group 限制最多 256 个查询和 4096 个等待者，满额返回 `limit`，不另起无界查询。停止顺序要求先停止新查询、取消各操作与各网络 owner、在对应 executor 排空，然后销毁缓存、group 和 executor；仅停止一个网络 owner 不会自动取消其他 executor 上作为 follower 的操作。

合并键包含配置代次、规范化名称、类型、view、数值上游、TCP、EDNS 和缓存策略；显式禁用缓存的组合器仍执行各自查询。缓存本身以 view、名称和类型为键，配置 owner 必须为所有影响答复的上游和选项分配兼容的 view，不能仅依赖事务键区分缓存数据。新 leader 在登记后重新查缓存，避免前次 miss 与其他查询填充之间的竞态；该重查同时取得正、负结果的绝对到期时刻，包括显示 TTL 0 的亚秒正结果。答复由每个等待者复制，正答复 TTL 按等待时间向下扣减；已知有效期的答复在慢等待者恢复前过期时，等待者在原 deadline 内重查缓存，未命中则重新登记查询。已完成事务可能仍被慢等待者固定，未命中时也可能因额度已满而返回 `limit`。分配失败返回限额错误。失败注册或发布不丢失网络成功答复，令牌在任务结束时回收。实验缓存的前台及统一事务后台发布另传取得时刻，以该时刻与剩余 TTL 算绝对到期，写锁等待不会顺延该期限；普通缓存接口和旧的独立后台刷新不使用此方法。

显式禁用缓存的独立查询现在也占用同一个前台 flight 上限：许可由查询协程独占，网络调用结束（包括超时或取消排空）才归还；满额返回 `limit`，已经存在的同键 flight 仍可接受未满额的等待者。停止的 executor owner 拒绝新直通查询，调用方仍须取消并等待已经开始的直通操作。epoll/io_uring 测试以两个 executor 同时占满 8 个许可，检查额外直通/合并查询均不发包、取消后复用、既有 flight 继续合并、超时与迟到回复及停止。另有仅测试启用的统一后台登记：同键刷新与前台共用事务，后台、前台及直通共同占额；旧的 `BasicRefreshOwner` 模式仍用独立预算，两种模式不能同时开启，任何一种均未进入生产。这个额度不限制调用者未登记的请求、内核内存或多个配置代次的总量。

统一事务的后台失败退避是尽力而为：每份 group 在构造时按网络事务上限预留同数固定长度键槽，失败后一秒内不新建同键后台任务，前台仍可查询；满槽时淘汰最早结束的退避，成功结果清除对应槽。在本机 GCC 16.2.1 的布局中，上限 256 时数组请求 83968 字节（每槽 328 字节），不含分配器元数据、事务及其他对象；此前的 `flight-memory-v3` 样本早于这一数组，不能视作新版本的内存测量。两个实际 executor 的真实 UDP 测试覆盖后台先行、前台先行、最后前台取消但后台继续、注册后缓存被填充、后台失败退避与重试、owner 停止和迟到回复；单槽被慢等待者固定时的正负缓存重查，以及三槽被后台、前台和直通共同占满时的拒绝、附着及复用也已验证。退避键的规范化、view、类型、上游、TCP、EDNS 隔离、满槽淘汰及登记分配故障经同步测试覆盖。

`DNS_GROUP_ALLOW_SUBSECOND_EXPERIMENT` 仅由独立目标和隔离检测构建启用：正/负缓存直到真实期限才失效，正值最后不足一秒返回 TTL 0，绝不延长期限；原始 TTL 0 仍不存入缓存，负值不变成 stale。定点测试覆盖跨组接纳、到期边界、stale 和原始零 TTL；真实 UDP 对端以 TTL 2 秒回应时，解析耗时保守扣除 1 秒，下一请求在余下不足一秒内：默认实验再次查询上游，候选命中缓存。`AddressResolver` 对整个解析耗时向上取整，线路 TTL 1 秒通常在写缓存前就变为 0，此候选不能解决该情况。是否允许对外返回 TTL 0、缓存替换和业务消费语义、以及真实负载成本仍需评估，不改变默认策略。

上游零 TTL（包括解析耗时保守扣减至零）及缺少 SOA 期限的否定答复不缓存；它们只交付给答复到达前已登记、尚未超过各自 deadline 的等待者，完成后的新请求不会加入旧 flight。这个实验选择把这些等待者视作同一次上游事务，即使 executor 随后停顿；[RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html) 规定零 TTL 只能用于正在进行的事务，不能缓存。零 TTL 正答复、零 TTL 否定答复和无 SOA 否定答复都以慢等待者和后续新请求验证。此策略与将每个调用视为独立事务的解释不同，产品接入前仍须决定是否接受及多长停顿可接受。

剩余限制：旧的独立后台 refresh 与前台 flight 仍可能重复查询；统一事务方案尚未接入正式代理。普通缓存及旧后台刷新的相对 TTL 发布接口遇到锁等待时对绝对到期的约束还需审查。`boost::corosio::timeout` 在其 `await_suspend` 中启动定时协程，而该路径由 `noexcept` 包装，尚未证明所有底层分配失败都可恢复。隔离检测不插桩预编译 Capy、Corosio 和系统库，不能代替长期并发、安全及完整故障审查。

#### 可借用的共享成员容量

用户进一步要求少数组也能使用空闲容量，固定每组 1024 项的候选不是最终方案。`DNS_GROUP_SHARED_CAPACITY_EXPERIMENT` 的独立候选把配置的总成员额度分给实际启用的 1–17 组：每个组在根中的每条成员引用占一个额度，相同 DNS view、名称和类型的多个组可共享答复节点，节点及各组的成员页、目录、历史根和待发布副本仍各自计入快照字节预算。实验编译上限 8192 个成员只是边界测试条件，不是产品默认或用户的配置建议。

候选规则是 `基础份额 = floor(总额度 / 启用组数)`；未使用的额度以及除法余数可由任意组借用。总额满时，先清理所有组中到达 discard 期限的成员；请求组未达到基础份额时，从超过基础份额最多的组收回一项，同额按组索引选择；达到基础份额的组只能替换本组最早到期项。每次请求最多收回一条，后活跃组随着自己的成功写入逐步达到基础份额，不主动移动已有答复。该规则保证的是成功提交、预算充足时的成员名额，而不是足量字节或真实缓存命中；配置变更仍需新 owner 并排空旧任务。不同权重、余数轮转、是否保留某些组的更大份额以及对预算耗尽的产品行为均未确定。

目录仅在组首次使用时分配，随页数按倍数扩张，写时复制以及目录增长时同时存在的旧、新目录均计入预算；删除成员后当前目录暂不收缩，直到清空或 owner 销毁。原型最少为每个活跃索引保留一个指针，最多 512 个指针；这不代表预先分配 17 组的成员节点。热路径仍需实际性能验证，满额写入须扫描组和页以检查到期项。快照预算不计调用者结果、任务、套接字、标准分配器附加成本或内核内存。

- `results-2026-10-30/cli-production-local-2026-10-31.jsonl`：local DNS、400 请求/秒、四场景两轮，每场 8 秒，合计 51,200 次全部完成，无漏投或失败。旧版测量期每请求发出 A/AAAA，新版热点、均匀与不重叠场景命中缓存；部分尾延迟样本波动较大。
- `results-2026-10-30/cli-production-local-high-2026-10-31.jsonl`：local DNS、1,200 请求/秒、四场景两轮。新版 76,800 次全部完成；旧版完成 76,676 次，124 次因驱动在途上限未投放，已发请求无失败。新版上游查询和 CPU 较低，但有漏投的旧版场次不能作为等量完成请求的直接延迟比较。

每种场景的两种版本交替运行，第二轮反转顺序；名称集合分别为热点、64 个共享名称、按入站分离的名称，以及 4 秒 TTL 的到期集合。预热后才开始计量。此测试为单机回环、短时固定投放，DNS 答复及目标均受控，不能代表跨机网络、持续生产流量、绝对进程内存上界或所有访问分布。`VmHWM` 包含进程其他状态；快照的 32 MiB 计费不包括所有调用方、协调器、分配器和内核内存。

`tests/dns_shared_production_memory.cpp` 直接构造生产 `SharedDnsGeneration(17, 257)`，以最大长度名称、16 个链名和 128 个地址的合成答复填满 4,352 个成员，随后让 reader 固定旧快照并替换答复，检查预算耗尽时关闭缓存、迟到 reader 不返回旧答复、释放后重建；再注册 4,096 个挂起 token，检查第 4,097 个触发限额、旧 token 失效及恢复。该入口用根包 `test-dns-resource` feature 单独构建，不为生产代码启用测试回调。release 图在本机独立进程三次运行均通过，峰值快照计费均为 33,548,076 字节，未超过 33,554,432 字节；进程 RSS 高水位分别为 39,388、39,412、39,592 KiB。这是极大合成缓存和注册状态，不包含真实网络并发任务、调用方保留的答复或完整内核内存；RSS 也受分配器和装页影响，不能作为全进程硬上界。此前独立事务/等待者的网络内存样本仍有旧布局限制，见上文。

### 可选反查核心的满额路径

`reverse_bench.cpp` 用 4096 条未过期记录填满仅实验图的 `ReverseCache`，在同一时刻分别重复更新已有地址和尝试写入未收录地址，各 50,000 次；固定单线程 CPU 4，GCC 16.2.1 release。维护保守的最早过期下界后，2026-10-31 交错两轮，满额新地址由约 5,887–6,062 ns/次降到 85–86 ns/次，已有地址更新约 83–92 ns/次；两版预分配表均为 4,981,344 字节。未到最早可能过期时跳过全表扫描，发生过期仍扫描并清理；无法保存的记录仍使查找在其 TTL 内全部退化为未知。该样本不覆盖碰撞、到期清扫、锁竞争、真实网络或所有容量，不是生产性能结论。

`tests/dns_reverse.cpp` 的 30,000 步独立模型覆盖容量、过期、迟到、冲突、视图和清空，并测试两族事务只在接受后发布、使用查询开始时间保守折算 TTL、乐观 stale 不发布和旧 epoch 被拒绝；当前这些代码没有连接生产 DNS。

实验 feature `test-reverse-observation` 将反查事务挂在真实共享协调器查询上，只用于 `nexus.dns-group-core/coordinator-module-test`。epoll/io_uring 均验证网络答复、缓存命中、同 IP 跨视图隔离与同视图名称冲突、A/AAAA 一致与 CNAME 不一致、stale 不发布、clear 后旧答复及取消。DNS 反查模块无条件导入，但其内容仅由 `nexus.dns/reverse` 功能编译；观察代码和测试入口只在上述 feature 中编译。无 feature 的协调器夹具通过，最终组合 release 未发现反查实现或观察钩子符号。实验不涉及实际代理配置的 DNS 视图选择、local search、流量查询、生产启用、性能或资源预算。

`tests/dns_reverse_allocation.cpp` 单独覆盖构造分配失败；在禁止 C++ 常规堆分配后执行 2000 次过期写入/查询、表重建、清空以及事务提交，确认没有调用常规 `operator new`。这不覆盖内核内存、其他分配接口或网络驱动。

反查试验将域名从两张哈希表移至按容量预分配的共享池，槽位保存 16 位索引；冲突、过期和清空回收池项，重建保留存活项的索引。4096 容量的 `storage_bytes()` 从 4,981,344 降至 1,835,104 字节，统计的是 vector 容量及元素大小，不包含对象、分配器开销或其他 DNS 内存。固定 CPU 4、相同 release 基准交错两轮，旧版已有项更新为 86–100 ns、新版 83–90 ns；满额新地址旧版 82–85 ns、新版 92 ns。样本短且受频率等环境影响，不能推断生产性能；它不覆盖到期清理、碰撞、竞争或网络负载。新增池满、冲突、回收及清空测试，逐次注入三个构造分配失败；原 30,000 步模型和禁止操作期间分配测试仍通过。
