# KDL 2.0 配置设计

状态：KDL 2.0 和解析库已确定；字段、节点及加载策略为设计草案。

## 格式基线

配置使用 UTF-8 编码的 KDL 2.0 文档。节点、参数、属性和子节点的语法以 [KDL 2.0 规范](https://kdl.dev/spec/)为准；布尔值示例采用 `#true`、`#false`。

解析库固定来自 [glaze-kdl2.0- 的 feature/kdl2.0 分支](https://github.com/hiykhello/glaze-kdl2.0-/tree/feature/kdl2.0)。库的解析成功仅说明语法和转换满足其实现要求，Nexus 仍需执行平台配置的语义校验。

## 加载流程草案

读取文件 → KDL 2.0 解析 → 类型化配置构造 → 语义校验 → 应用装配。

语法或配置校验失败时，不启动新的网络组件。建议错误包含文件路径、节点或字段路径和原因；行列定位是否可用需核实解析库。

## 配置模型草案

| 节点 | 拟定含义 |
| --- | --- |
| `schema-version` | Nexus 配置结构版本，与 KDL 语言版本分别管理 |
| `role` | 部署角色，示例使用 `client` 或 `server` |
| `inbound` | 具名入站，描述监听及协议处理 |
| `outbound` | 具名出站，描述连接目标的方式 |
| `routing` | 路由选择及默认出口 |

早期示例使用 `tcp-forward` 和 `direct` 表达最小静态转发关系；[配置规范草案](spec.md)进一步展示 Mixed、TUN、VLESS/TLS、DNS、规则及控制面的拟定字段。这些名称均不表示已实现或构成最终配置契约。

## 语义规则草案

- `schema-version` 必须受当前实现支持；初始示例使用整数 `1`。
- `role` 必须是当前实现支持的角色，角色与启用组件需要一致。
- 同类具名组件的标识唯一，所有路由出口引用必须存在。
- 监听与目标地址、端口、协议参数需按组件类型校验。
- 未知节点、未知属性和缺失必需字段建议作为错误处理。
- 单值节点重复、默认值及覆盖规则需在实现前明确。

KDL 对重复属性规定后出现的值覆盖先前值。若 Nexus 希望额外拒绝重复属性，需要确认解析层能否保留原始信息，不能假设转换后的对象能检测所有重复项。

配置包含与环境变量替换尚未定义；密钥文件引用及热重载的行为草案见[配置规范](spec.md)。早期静态转发示例不依赖这些能力。

## TUN 与 TLS 的后续扩展

已确定加入自研 TUN 与 TLS/uTLS 类能力，具体 KDL 节点和默认值尚未冻结；[成对示例](examples/README.md)只是展示拟定字段，不表示已有配置支持。

建议 TUN 配置分别表达设备与地址、路由/DNS、资源预算、UDP 映射和过滤行为，不引入历史上的多网络栈切换选项。TLS 配置分别表达连接地址、验证身份、信任策略与 profile，profile 不隐式关闭证书验证。引用不支持的算法或未编译的能力应作为配置错误。

配置解码类型与组件工厂的配对注册见[组件模型](../architecture/component-model.md)，自研范围见[TUN](../architecture/tun.md)与[TLS](../architecture/tls.md)。

参见[配置示例](examples/README.md)。

## 规则集文本与二进制

规则集另采用 KDL 2.0 文本和 BEVE 二进制，并提供双向转换，共享规则语义校验；规则 schema 与本页主配置 schema 分开。反向导出为规范化 KDL，不承诺恢复注释与排版。当前谓词子集及 Linux 转换命令见[规则集互转](rule-sets.md)；更复杂的规则仍待设计。
