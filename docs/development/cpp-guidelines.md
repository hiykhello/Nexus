# C++ 编码与错误处理规范

状态：本文的语言风格与能力优先级为已确定要求；错误类型和具体接口为设计草案。

适用于 Nexus 自有 C++ Modules、组件 facade、协程边界及第三方适配层。本机部分语言与库能力已做最小编译探测，实际项目与第三方依赖的支持范围按构建和测试结果记录。

手写代码文件的行数目标、上限及例外规则见[代码文件行数规范](file-sizes.md)。

在外部输入、资源获取和并发边界验证实际可能失败的条件；内部已由类型或调用契约保证的不变量不要层层重复检查，也不要为假设中的故障增加回退分支、包装层或测试矩阵。检查应对应明确的风险和处理方式，保持正常路径易读。

## 语言能力与风格

项目代码优先使用标准库命名模块 `import std;`。宏、平台 API 和需要以头文件接入的第三方库仍使用相应头文件；例如 `errno` 需要 `<cerrno>`。模块单元中这些头文件位于 global module fragment，模块声明后再导入 `std`；不把头文件单元当作命名模块替代品。

优先使用本机 GCC 已提供并经验证的 C++26/C++23 能力，不为兼容尚未要求的旧工具链退回旧式写法。当前本机探测结果见[GCC 能力记录](gcc-capabilities.md)，项目默认语言方向为 C++26，依赖可按其接口要求单独适配。

函数优先使用后置返回类型：`auto function(...) -> Type { ... }`。公开接口显式写出返回类型，避免依赖实现体推导接口；构造、析构、转换函数等语法不适用处保留对应语言形式。

非静态成员函数优先使用 C++23 显式对象参数，例如 `auto size(this Buffer const& self) noexcept -> std::size_t`。这里的“显式 this”指 `this Type& self` / `this auto&& self`，不只是给成员访问补 `this->`。按需求表达 const、引用与值类别，避免无必要地把每个成员都写成转发模板。显式对象成员通过 `self` 访问对象，不能依赖隐式 `this`；构造、析构、必须覆写的虚函数等不适用处按语言或外部接口要求处理。

模板约束优先使用命名 concept 与 `requires`，不以 `enable_if`、返回类型 SFINAE 或深层模板错误代替可表达的接口约束。约束描述调用所需的能力；编译期不变量和实现内部检查使用 `static_assert`。

```cpp
// 语言风格示例；不是已冻结的项目接口。
struct Buffer {
    std::size_t size_ = 0;

    auto size(this Buffer const& self) noexcept -> std::size_t {
        return self.size_;
    }
};

template<class T>
concept Sized = requires(T const& value) {
    { value.size() } -> std::same_as<std::size_t>;
};

auto buffer_size(Sized auto const& value) -> std::size_t {
    return value.size();
}
```

示例依赖相应标准库声明；正式实现遵循项目 Modules 组织方式。

## 多态与静态反射

项目自有的动态多态接口使用 ngcpp/proxy facade，明确所需能力、对象所有权、生命周期和异常保证。禁止在项目自有设计中以虚函数和继承实现动态多态，包括自定义虚接口及其覆写实现。对第三方已有虚接口进行必要适配时，遵循该接口要求；这不改变项目自有接口的规范。编译期可确定的能力优先用模板与 concept 表达，单签名回调按下文选择。

建模类型关系时先考虑组合，以成员对象表达持有和协作；当继承能清晰表达关系且合适时，允许普通的非虚函数式继承。本规范不禁止普通继承，也不要求为了避免继承而引入不必要的类型擦除。

需要编译期结构信息、成员枚举或由类型生成元数据时，优先使用 C++26 原生静态反射。不要因历史习惯优先引入额外反射库或重复登记成员的宏体系。本机 GCC 反射需启用 `-freflection`；具体反射操作及跨 Modules 行为仍须分别验证。

原生反射可用于项目自有类型的元数据、校验与映射，但不改变已确定的 KDL 2.0 解析库选型。与指定 glaze-kdl2.0- 分支如何配合仍待验证，不能宣称该分支已支持本机反射接口。

## 函数包装与回调

按调用、所有权与复制需求选类型，不默认使用 `std::function`：

| 需求 | 优先选择 | 生命周期约定 |
| --- | --- | --- |
| 调用对象类型可在编译期确定 | concept 约束的模板参数或直接保存具体类型 | 避免无必要的类型擦除 |
| 同步借用可调用对象，无需取得所有权 | C++26 `std::function_ref<Signature>` | 不延长目标寿命，不能借用短命对象后留待异步调用 |
| 拥有回调，允许仅移动 | C++23 `std::move_only_function<Signature>` | 适合持有唯一资源或异步任务回调 |
| 确实需要复制拥有的回调 | C++26 `std::copyable_function<Signature>` | 目标应满足复制要求，明确复制的业务含义 |

需要多种操作组成的动态能力接口时使用 ngcpp/proxy；单个函数签名的回调按上表选择。`std::function` 仅在既有外部接口等实际约束下使用，不作为新接口默认类型。

按调用需求保留 const、引用和 `noexcept` 签名约束；不为迎合包装类型而无依据地承诺不抛出。拥有型包装不等于闭包中借用的对象也被拥有，异步回调仍需检查捕获对象寿命。调用前满足有效目标的前提，不依赖空包装调用来生成错误。

## 断言

能在编译期判定的内部条件优先使用 `static_assert`；运行期内部不变量优先使用 C++26 `contract_assert`，不将传统 `assert` 宏作为新代码的默认方案。

只采用契约断言这一能力，不使用函数级 `pre`/`post` 契约说明符，也不另建普通契约框架。契约断言表达式保持无副作用，不能把必须执行的操作放进断言。

外部输入、配置错误和可恢复失败仍使用校验与 `expected`，不由断言代替。构建需明确契约断言的检查语义；仅编译通过不能证明运行时一定执行检查。契约断言不作为异常控制流使用。

## 返回值表达语义

| 场景 | 优先表达 | 约定 |
| --- | --- | --- |
| 必然产生一个值 | `T` | 不为普通返回值额外包一层 |
| 成功或有原因的失败 | `std::expected<T, Error>` | 错误携带可处理的原因 |
| 无返回值的可失败操作 | `std::expected<void, Error>` | 成功返回空的成功状态 |
| 正常情况下可能没有值 | `std::optional<T>` | 缺失本身不是错误，无需提供失败原因 |
| 可失败且成功时可能无值 | `std::expected<std::optional<T>, Error>` | 仅在确有三种状态时使用，避免不必要的嵌套 |

例如：配置解析失败、连接失败和 TLS 握手失败使用 `expected`；可选配置项及正常的查询未命中使用 `optional`。必须存在的组件引用未找到属于校验错误，不能仅返回空值并继续启动。

不要用 `optional` 丢弃错误原因，也不要用默认对象、空字符串或 `bool` 加输出参数代替需要详细错误的结果。流结束、等待更多数据等协议状态应明确建模，不能一概归为失败。

## 异常策略

业务流程和预期失败尽量不使用异常。配置错误、无效输入、I/O 失败、超时、取消和协议失败优先通过显式结果或明确的状态类型传播，避免以 `throw`/`catch` 组织普通控制流。允许异常时，应在合适的边界尽力捕获并处理可识别异常，保持资源清理和明确的失败报告；不承诺所有异常都能恢复。

“尽量无异常”不等同于已经承诺全项目使用 `-fno-exceptions`。标准库分配、第三方实现及协程运行时可能存在异常路径，需逐项核查。不得仅因函数返回 `expected` 就宣称它绝不抛出。

如第三方 API 只能通过异常报告错误，应在明确的适配边界处理可识别异常，转换为项目错误；记录尚未覆盖的异常及处理策略。不要吞掉异常后返回成功，也不要在每一层增加宽泛的 `catch (...)`。

用户已放开异常限制；在其自维护的新标准库完成前，继续使用现有标准库和依赖，Capy 保留异常运行。内存分配失败导致进程退出是预期行为，无需将其转成可恢复错误或重试。`nexus` 不再替换全局分配函数，普通分配使用标准库行为；实际退出机制取决于异常边界与第三方实现。历史实验见[无异常与可恢复分配路线](../planning/fallible-allocation.md)。

容器选择需分别考虑容量、分配和元素操作。标准动态容器没有通用的可恢复分配失败插入接口；预留空间也不能消除长度错误、元素构造或第三方分配器等其他异常路径。对于合理且编译期确定的上限，C++26 `std::inplace_vector` 的 `try_push_back` / `try_emplace_back` 可在容量满时返回空结果；本机 GCC 16 已用 `-fno-exceptions` 验证填满、拒绝和释放后复用。元素构造和移动仍需单独验证，普通 `push_back` 的满容量行为不同。Boost `static_vector` 也不能仅因有内嵌存储就断言插入绝不抛异常：元素操作可能抛异常，关闭溢出异常选项也要求调用方严格保证容量（[Boost 文档](https://www.boost.org/latest/doc/html/container/configurable_containers.html)）。

运行时配置上限的队列可评估预分配环形队列，以显式结果处理队满和背压；单 owner 结构无需为此引入无锁 SPSC。预分配槽位不会消除所持 `vector` 等元素的动态分配，也不能保证其他异常路径消失。替换流表时须保留既有对象地址稳定性、生命周期、删除和满容量语义；不能将队列直接当作链表的等价替代。采用可失败分配容器时，应分别评估第三方依赖和错误契约，内存耗尽、容量限制和 I/O 故障均作为可预期结果报告。

Abseil 也是容器与工具库候选，按具体使用场景评估而非整体替换标准库。`absl::InlinedVector` 是小缓冲优化，超出实际内嵌容量后仍动态分配，并非固定容量容器；`flat_hash_map` 重哈希使元素指针失效，`node_hash_map` 保持节点地址但单独分配节点（[Abseil 容器指南](https://abseil.io/docs/cpp/guides/container)）。上游明确声明 `flat_hash_map` 不具备异常安全保证（[头文件](https://github.com/abseil/abseil-cpp/blob/master/absl/container/flat_hash_map.h)），因此混合异常代码时需审查操作及回滚，不能把禁用异常等同完整故障处理。`ABSL_ALLOCATOR_NOTHROW` 是对默认分配器行为的构建期声明，不是分配策略本身，必须按整个构建及实际分配路径验证，不应只因可执行文件替换了部分分配函数就全局启用。

本机系统 Abseil 20260817.0 用 GCC 16 `-fno-exceptions` 编译简单消费者，计数分配器观察到 `InlinedVector` 填满实际初始容量前无分配、随后增长分配；`flat_hash_map` 基本插入和查找通过。实际初始容量可大于模板参数。此实验链接系统预构建库，未验证其编译选项、故障语义、项目 Modules 接入或性能，也未将 Abseil 纳入正式依赖；正式选用前须锁定版本并验证这些方面。

## 结果检查与错误类型

可失败接口建议标注 `[[nodiscard]]`。调用方必须检查结果、处理失败或向上传递；明确忽略时需能说明其合理性。

对 `expected` 和 `optional`，优先在状态检查后使用 `*`、`->`，避免未经检查调用 `.value()` 引入异常路径。未经检查解引用同样不允许；`.value_or()` 仅用于有明确业务默认值的场景。

建议 `Error` 至少区分错误领域与稳定错误码，并按需附加系统错误、组件标识和操作上下文。错误码供程序判断，文字描述供诊断，不能通过匹配错误文本决定控制流。具体结构与存储策略待验证，尤其需要考虑错误路径的内存分配。

考虑使用静态只读映射将错误领域与代码转换为固定描述；每次操作通过自身的结果值携带错误及必要上下文，避免并发会话共享可变的“最后错误”。该映射是待验证的设计，不保证所有错误上下文可无分配表示，也不是已完成的全局错误类型。

底层保留原始错误，跨层传播时补充上下文，日志尽量在最终处理错误的位置记录，避免同一失败被逐层重复输出。

## 构造、资源与关闭

需要读取文件、创建网络资源或执行其他可失败工作的对象，优先由返回 `expected` 的工厂创建；构造函数建立对象的不变量，避免把部分初始化对象交给调用方。

资源采用 RAII 和明确所有权。析构不抛出，执行最终释放；需要返回错误或等待异步操作的关闭，使用独立的显式关闭接口。关闭失败应保留诊断，但不能使清理链提前中断，导致后续资源未释放。

### 共享所有权

`std::shared_ptr` 和 `std::weak_ptr` 必须极其谨慎使用，不作为延长对象寿命或简化异步代码的默认手段。优先使用值、明确的单一所有者、`std::unique_ptr`、作用域内借用，以及取消后等待所有任务退出的生命周期设计。协程挂起、回调捕获、跨线程传递或测试方便，均不单独构成引入共享所有权的理由。

只有确实存在多个相互独立、无法以明确的所有者及其生命周期安全管理的所有权方，且单一所有权或借用方案不能满足需求时，才考虑共享所有权。引入时须在相关设计或代码中说明所有者、共享的必要性、最后释放条件和取消/关闭顺序，并检查引用环、并发访问、分配与引用计数成本、析构位置及资源上界；对性能敏感路径还须验证实际成本。`weak_ptr` 不能替代明确的生命周期和同步约定。评审已有或新增用法时应主动寻找可安全简化为单一所有权的方案，不因现有实现使用共享指针就默认继续沿用。

`noexcept` 只在调用链及所用操作能满足约束时标注。返回 `expected`、移动操作或性能敏感都不是无条件添加 `noexcept` 的理由；违反约束可能导致进程终止。

## 协程与 facade 边界

异步操作同样显式表达成功和失败。概念上使用“承载 `std::expected<T, Error>` 的异步结果”，实际任务类型和错误转换方式按 Corosio/Capy 的接口验证后决定，不预设不存在的库 API。

需要核查任务创建、协程帧分配、`unhandled_exception`、等待操作、取消与清理的错误语义，不能只约定最终返回值。取消和超时需要可区分，是否记录为错误由调用场景决定。

ngcpp/proxy facade 应保留实现操作的结果类型与异常保证。声明 `noexcept` 前验证所有被包装实现，避免在类型擦除边界隐藏异常或错误信息。

## 标准与构建

`std::expected` 和 `std::move_only_function` 属于 C++23；`std::copyable_function`、`std::function_ref`、原生静态反射与契约断言按 C++26 能力采用。项目优先使用本机已提供的 C++26 能力，C++23 是 expected 等能力的基础要求，不是要求项目停留在 C++23。

本机 GCC 16.2.1 的最小编译结果见[能力记录](gcc-capabilities.md)。当前 mcpp 工作区以 C++26 和反射选项构建规则集模块；契约检查语义及其他依赖的跨模块使用仍需验证。

构建验证需覆盖：Modules 中导出结果类型、跨模块返回与使用、第三方错误适配、协程失败，以及启用和禁用异常时各依赖的实际限制。用户要求全项目无异常；目标是项目代码和依赖的可预期失败均以结果值表达，分配失败也应以结果值表达且不直接终止。当前尚有依赖抛异常及项目中的异常边界与回滚，不能声称已实现。先逐项改造并验证第三方契约和资源回收，再在隔离构建中启用 `-fno-exceptions`，通过完整构建和故障回归后推广；现阶段不得以全局编译开关掩盖未改造的错误路径。
