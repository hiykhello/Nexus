# 模块与可选功能

项目使用 mcpp 工作区组织有实际职责的包，不为每个目标生成虚假子包。源码中的命名模块导入采用无条件 `import`；参与编译的每个导入，都必须在同一构建图中有且只有一个可用的模块提供者。feature 和依赖声明必须与实际源码、模块和链接关系一致，并以实际构建验证。

内部名称优先直接表达职责。新建内部模块、目录和实现符号时，省略重复的 `nexus` 前缀，例如容器模块使用 `containers.*`。已有名称随组件重构分批精简，优先处理只在仓内使用的名称。有实际冲突、外部消费者或兼容约束的名称按具体边界处理。迁移时同步核对模块声明、导入、构建配置和受影响的调用方。

优先保持调用方所需的公共 API 一致：不同配置提供同样的类型与函数签名，功能关闭时由实现明确返回不可用，而不是假装执行成功。仅为统一构建不引入虚函数、运行时分派或额外分配。接口需要的类型也必须在所有使用它的配置中存在。

如果功能的 API 本身就是可选的，可以让导出随配置变化，但所有使用缺失 API 的调用代码也必须受同一配置控制。模块名一致本身不保证 API 一致。无论采用哪一种方案，都要验证关闭、开启和组合配置，检查编译器实际模块依赖、对象、链接和行为。

这里的签名一致指同一配置中所有调用方看到一致的源码接口，不保证不同 feature 构建的二进制 ABI 可以混用；私有布局和模块 BMI 可能随配置变化，切换时必须重建受影响的依赖。对从未请求的可选功能，空的生命周期操作可以成功；配置中明确请求已关闭的功能时必须返回失败。

此前尝试让同一源文件的条件导入随 feature 改变，并用固定扫描声明覆盖多个配置，未能成功。独立工作区的特定条件导入实验曾通过，不能据此称生产配置已迁移。以当前约定继续，不以堆叠扫描覆盖或人为复制包掩盖不一致。

禁止在新代码与重构中引入文本 `#include`；现有遗留包含逐步迁到命名模块。迁移不得改变随机数、所有权、取消、排空及错误行为。Linux x86-64 是本轮验收范围。
