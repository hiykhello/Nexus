# 无异常与可恢复分配路线

状态：已归档（不计划实施）。用户已放开异常限制，项目继续使用标准 C++ 库（`libc++` / `import std;`）与现有依赖，没有自建标准库、引入 AK 或将 Capy/Corosio 改为无异常的计划。下文仅保留原方案与实验背景，不作为当前实施要求。正式二进制已移除全局分配替换。

原正式 Linux 二进制的全局普通 C++ 分配替换在失败时调用 `abort`；该替换现已移除。普通 throwing `operator new` 返回空指针违反其调用契约。标准容器、第三方分配、协程帧、服务对象和系统库具有不同的失败行为，不能通过全局开关统一推断。

优先步骤：

1. 固定、集成并逐步以 AK 替换项目动态容器；独立验证 AK 的可失败容器（初步 Vector 故障及容量溢出探测见 `experiments/ak-fallible/`），核对 Linux 主机构建、依赖及许可、GCC 16 C++26、`-fno-exceptions` 和项目模块封装。测试 `try` API 在分配失败时报告错误、保留已有数据和允许后续重试；检查所有包装、元素操作与溢出路径是否终止或抛异常。`ErrorOr` 与项目结果类型在边界转换，避免错误路径再次分配。
2. 在真实业务路径逐步替换可失败动态分配及相关调用链；固定容量和预分配结构在容量满时报告结果。对每次失败验证既有资源不泄漏、状态可继续或明确关闭；避免仅测试容器本身。
3. 全面改造 Capy/Corosio 的执行状态、协程帧、服务、线程池和后端初始化，保留取消、失败结果与清理；包含创建、部分启动和运行期间的故障注入。现有实验补丁有直接终止的探测分支，不满足新要求。
4. 审查 TLS/加密、DNS、解析器、日志、配置等第三方和系统调用：包括直接 C 分配及已知会终止的依赖，选择可报告失败的实现或改造；不能把 C++ 全局分配钩子视为覆盖全部分配。
5. 在所有正式路径迁移完成后移除旧全局终止策略，以隔离 GCC 16 无异常全量构建及逐点故障注入验证，覆盖初始化、服务运行、并发、错误报告和退出；检查内存耗尽不导致异常传播、abort、错误丢失或资源泄漏。

错误类型、错误记录、回滚及清理也必须无需新分配。第三方及标准库内部可能仍存在不可恢复失败或进程终止路径，必须明确识别并实测，当前不能宣称实现了本目标。

全面迁移不是简单替换类型或只关闭异常编译选项：须覆盖 AK 本身及其 `MUST`、`VERIFY`、不安全别名和溢出路径；Capy 和 Corosio 的协程分配、执行器、全部实际启用后端及错误处理路径都需返回可处理结果。保留能力、协议行为和资源生命周期；不因先前试验通过就将某个依赖视为完成。
