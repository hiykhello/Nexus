# DNS 共享缓存方案评估

2026-10-30。用户建议评估 Xenium 和 Maged Michael 的 hazard pointers，减少每 worker 一份 DNS 缓存的重复占用，也允许维护专用数据结构。生产路径目前有一个共享锁缓存候选，读取性能仍不满足目标；下述其他方案仅为实验，尚未决定生产实现。

## 现状

原有配置 DNS 的 `DnsState` 每 worker 有最多 256 条 `AddressCache`，相同记录和未命中查询会跨 worker 重复；256 是条目上限而不是预分配。工作树里的共享锁候选让多个 worker 使用同一缓存，真实 2/4 worker 的 A 和 AAAA 共享命中已验证，但其热点读延迟仍高。local DNS 当前绕过该缓存；Shadowsocks UDP 各密钥组运行在一个独立执行器，工作树中改为共享一份缓存，仍与 TCP worker 缓存分开。缓存键包含解析视图、规范化名称和类型，现有视图是配置内的服务器索引；共享时必须确保它只在相同配置和生命周期内有相同含义。

缓存不只是键值表：正负 TTL、有限 stale 窗口、容量淘汰、查询令牌、同键发布顺序、clear 代次及 stale 条目 revision 共同决定结果。后台刷新 owner 仍属于单执行器，尚未进入生产；如果缓存共享，刷新去重、实际运行任务上限和停止排空也必须跨 worker 定义，不能只共享存储。后台 I/O 和取消仍应留在所属执行器，不跨线程操作其 socket。

## 候选和约束

- 共享分片缓存：用有限数量分片分别保护数据和令牌，以共享的总容量替代每 worker 容量；先作为语义与性能基线。锁只覆盖内存操作，绝不跨 `co_await`。需要明确分片配额、跨分片 clear 的线性化、时间读取顺序、停止和配置重载的生命周期。当前缓存的全局单调时间检查不能直接接受在取得锁之前采样的乱序时间。
- Xenium：其 [harris_michael_hash_map](https://mpoeter.github.io/xenium/classxenium_1_1harris__michael__hash__map.html) 是固定桶数的并发 map，支持可配置回收器；[项目](https://github.com/mpoeter/xenium)提供 hazard pointer 等回收方案。hazard pointer 解决并发读者仍持有已移除节点时的安全回收，不能自动解决条目更新、容量淘汰、查询排序或跨 worker 刷新限制。需要核查迭代器/guard 的线程归属和析构，不能把 guard 跨协程挂起或执行器迁移；回收延迟、线程本地元数据及退役节点也必须计入总内存上界。固定桶数量、热点和碰撞需要测量；容器 lock-free 不等于整个缓存操作或分配器 lock-free。
- [mm_hp](https://github.com/magedm/mm_hp)：用户补充的候选，初查固定提交 `b26e5edc779bf2afaea821549c04bf0a07b20f11`。这是 C++26 hazard pointer 的实现参考，不提供并发 map；需要自行设计容器或适配现有容器。上游许可可选 MIT 或 Apache-2.0 with LLVM exception；README 将范围限定为 Linux x86-64 和 GCC，源码使用 `std` 命名空间、Linux `membarrier` 及非头文件实现。它不适合直接与 Xenium map 当作同类组件比较：应在相同数据结构、相同缓存语义下比较回收策略。固定版本中回收默认至少积累 1000 个退役对象才触发扫描，且使用进程级域、线程局部记录缓存；回收重路径注册 `membarrier` 失败时中止，需评估运行环境、系统调用失败、保留内存与停机要求。是否可与项目标准库模块共存及完整失败行为尚未验证。小型生命周期探针见实验目录，不能代替安全审查或完整基准。

不预设无锁方案更快或更省内存。必要时分别比较不可变值替换及同步策略，确保读者只获取完整版本，且过期、清空、替换和查询发布具有明确定义的线性化点。不得把缓存视图隔离或 DNS 策略合并作为节省内存的代价。

## 固定上游实现的参考

- [Unbound 的 slabhash](https://github.com/NLnetLabs/unbound/blob/e78d0a1c03e40602e81d0c440190134106cf6ffc/util/storage/slabhash.c) 按散列分配到多个独立的 LRU 表，并把内存预算分给各表；分片减少锁争用，也意味着淘汰在分片内进行。
- [CoreDNS 的 cache](https://github.com/coredns/coredns/blob/f79be2a2f8266c2881d01f4c884149e8067569c9/plugin/pkg/cache/cache.go) 使用 256 个各自带读写锁的分片和随机淘汰。
- [dnsdist 的 packet cache](https://github.com/PowerDNS/pdns/blob/beef82f16e0a49a6ce7c3e23ed1fe59d4dd27ee5/pdns/dnsdistdist/dnsdist-cache.hh) 使用可配置数量的分片，每片保护一个共享 map，并提供可推迟插入的锁策略。
- [Envoy dynamic forward proxy 的 DNS cache](https://github.com/envoyproxy/envoy/blob/b49ebcf3451ffe9f758ead561549c0dea0b0328b/source/extensions/common/dynamic_forward_proxy/dns_cache_impl.cc) 维护共享主表，未命中时把加载送到主线程；还使用线程本地状态协调完成通知。这些是各自工作负载的设计，并不证明其中任何方案可直接满足本项目的 TTL、配置视图、取消或性能要求。

## 实验进度

`experiments/dns-shared-cache` 的固定容量风险指针表、带缓存语义的逐项风险指针表和不可变快照表均未接入生产。最后一种以每 worker 独占的保护槽读取共享不可变版本，写入串行、复制索引并原子发布；读路径不为每次命中增加 `shared_ptr` 引用。其差分、并发、故障和慢读者实验以及复现命令、原始数据和局限见实验 README。固定 256 个活动条目并不意味着历史内存是全局常数：停滞读者可分别固定不同版本，释放后也需要后续扫描或析构回收。读者必须在同步查询内独占槽，不能让保护跨协程挂起，生命周期和重入约束仍需生产设计。

有序快照已作为 `AddressCache` 的可选模式接入模块，仅独立测试代理启用；普通 Nexus 仍用共享锁。最多 256 项的排序索引二分查找，使查找不依赖散列安全；代价是字符串比较和每个读者预留约 2 KiB 快照。模块版本的缓存语义、竞争检测及 2/4 worker 正负命中验证已通过，固定速率实验和分配成本见实验 README；对所有生产监听器共享、执行器注册与真实代理负载仍未完成。空缓存时预留开销大于原始每 worker 缓存，慢读者可以固定多份历史数据，不能把常态初始化数字当成峰值。

正式模块现预留至多 `读者数 + 2` 个索引槽的地址空间，但仅在首次使用各槽时初始化；单进程 257 读者空表初筛的 RSS 增量下降，虚拟地址预留与最坏历史版本上界不变，具体结果及测量误差见实验 README。缓存还会压缩移入的超大预留缓冲区：待处理键及已保存答复的名称容量限于 254，CNAME 链容器限于 16，地址容器限于 128；这些数字限制保留的容器容量，不包含分配器开销或调用者传入的大缓冲区在调用期间的瞬时峰值。当前上界仍随读者数增长，且每份答复可包含多个长名称和地址，生产接入前必须按实际允许的读者数、并发查询及任务资源核算整体峰值。

同机初筛里快照的只读 p99 优于当前每 worker 缓存，8 worker 时初始化分配字节也少于 8 份缓存；固定投放混合实验多数请求完成，但部分轮次的热键 p99 高于每 worker 缓存。实验时间短，跳过的请求不计入延迟，仍不能证明真实代理性能。快照仍须验证真实负载、碰撞攻击、长时间及峰值内存、令牌和清空语义，并解决多 worker 后台刷新及 TCP 与 SS UDP 之间的生命周期。不能据此宣称满足性能目标。

去除访问钩子的真实 SOCKS/UDP DNS 回环测试在 800 请求/s 下完成两轮，独立多会话测试验证了挂起查询的取消、DNS 视图重启及迟到回复；一次 1600 请求/s 的反序轮次发生大量超时和漏投，单场重跑恢复，根因仍待定位。该负载生成器和本地 DNS/目标共享 Python 事件循环，延迟主要受测试端及本地网络影响，不能据此判断缓存带来的亚微秒差异；失败数据和可复现命令见实验 README。

SS UDP 的共享缓存按一次启动持有：所有密钥组使用同一 DNS 配置和串行执行器，停止时取消并排空所有监听器，再销毁缓存；下一次启动建立新缓存，避免同一视图索引沿用旧配置的值。独立互通对端测试覆盖跨组正负命中、不同视图、禁用缓存和挂起查询停机；同一 owner 用两个持续客户端更换 DNS 上游后重新启动，验证旧值不复用且新值再次跨组共享。启动逐位置分配失败覆盖首个监听器绑定后的回滚及重试。这些结果没有解决 TCP/UDP 跨执行器共享或跨 worker 刷新协调。

## 多入站的容量和生命周期

不能把所有入站直接指向同一个 256 项缓存：两个入站各访问 256 个互不重叠的域名时，固定顺序的容量轨迹在预热后产生 1024 次未命中；各自保留 256 项则全部命中。共享 512 项锁缓存可容纳该轨迹，完全重叠的轨迹则只需保存 256 条。复现程序和限制见实验 README；这是特定顺序下的容量语义，不是代理性能测试。当前快照最大 256 项；简单将其扩为所有入站容量的总和，也会增加每份快照的索引复制与慢读者可能固定的历史数据，必须测量。

容量求和也不保证隔离：确定性轨迹中，A、B 各填 256 项且 B 的 TTL 较短，A 再写 256 个不同名称时，两份 256 项缓存仍保留 B 的全部有效答复，而 512 项共享锁和分页实验均淘汰 B 的全部答复。各方法的淘汰规则都选最早到期项；该轨迹并不表示真实流量一定出现这种结果。下一候选需给每入站单独的有界成员索引，同时在可证明相同的视图中共享不可变答复，并单独核算跨入站更新、未命中接纳、旧版本及刷新任务的成本和语义。

单线程成员索引模型已验证上述容量轨迹及完全重叠的去重：每组独立淘汰，兼容视图首次命中其他组现有答复时把引用计入本组；同键发布在所有引用它的组中生效，清空覆盖共同 owner。它没有并发、查询代次、stale、异常回滚或性能保证，尚不是生产方案。不同语义配置不得仅因服务器索引相同而共享；独立清空也不能悄悄从另一组重新接纳清空前的数据，需通过清空共同 owner 或更换配置代次实现明确边界。

分页成员索引实验在相同根中实现这一模型，覆盖 17 组、每组 256 项的当前成员数、跨组去重、同键原子更新、读者历史、并发和分配失败回滚。现已加入正负缓存、stale/刷新和共同清空代次，单组 30000 步与现有锁缓存差分通过；跨多个组更新失败的回滚测试发现并修正了临时节点所有权错误。另用逐组复制值的独立模型验证了 17 组、四视图和两种查询类型的 20 万步随机轨迹。它仍缺网络任务和生产生命周期验证；跨入站接纳需要写锁，跨组同键更新需修改多个索引，真实多入站和 SS UDP 流量仍须测量。

有界当前成员数并不限制读者固定的历史答复总量。若 17 组各 256 条都不重叠，257 个读者分别固定不同的完整历史、每个历史之间全部重写，则可以同时保留 `(257 + 1) × 4352 = 1122816` 个不同版本的答复（还未计构造期间临时版本）。现有接口允许每份答复有 16 个链名称和 128 个地址；即使仅按每个键和 17 个名称各 200 字节、每个地址 17 字节计，这种人为极端轨迹也有约 6.04 GiB 的逻辑数据，还不含对象、索引、分配器或待处理任务；该组合是接口级最坏构造，未声称可由单个实际 DNS 响应产生。正式实现需要明确全局字节预算及预算耗尽后的安全行为，不能把空缓存 RSS 或 4352 条数上限当成进程峰值。

实验成员索引现可设置快照计费额度，旧读者固定的版本及构造副本都计入。无法发布时关闭缓存、清除登记并要求共同 clear 后恢复；epoch 防止恢复后的旧读者返回被清空数据。跨组接纳的额度失败只造成一次 miss。此额度不含分配器、查询/任务、调用方缓冲区等，不能称为进程内存上限；前台登记调用之前的参数分配也需在未来 owner 中覆盖。相关线程、故障与恢复测试和限制见实验 README。低预算可能导致全局旁路和上游请求激增，尚未决定默认值、恢复机制或是否采用该方案。

在独立进程的极端输入样本中，4096 个 253 字节名称的待处理登记使 glibc 分配增加约 1.45 MB，而快照计费不变；清除登记后其 vector 容量仍保留。固定历史的小答复实验中，17 组互不重叠、4 个读者持有旧版本时，4 MiB 快照额度触发全局旁路；读者释放且共同 clear 后可重新登记和发布。另一个 32 MiB 样本固定 21760 个节点时，快照计费峰约 9.77 MB、分配增量约 11.55 MB。两者都不含真实网络任务和生产负载，详见实验 README。

后续进程级 owner 应持有完整、不可变的 DNS 配置代次。只有上游地址及解析链、传输、EDNS、策略和规则均属于同一配置时，服务器索引才具有相同视图含义；重载时创建新 owner，停止并排空旧任务后再释放旧 owner，迟到回复只能针对原来的缓存及 token。系统解析目前绕过该缓存。服务器 worker 以及单线程 SS UDP executor 借用 owner：每个使用快照的 executor 独占一个同步 reader，最多 16×16+1 个；reader 不得跨挂起，停机先取消并排空网络任务，再释放 reader，最后销毁 owner。启动中途失败须按相反顺序回滚，不能留下已登记的槽。上述是待实现的生命周期约束，不是已接入的接口。

独立 `RefreshBudget` 已提供跨 executor 的实际任务上限、同键去重和有限退避；单个任务的租约比缓存发布 token 活得更久，取消后仍须等协程排空。预算目前只识别视图索引、名称和类型，因此只有同一配置代次才能共享它。若采用按入站分开的缓存，跨缓存去重还需要明确结果如何传播给其他缓存；不能假设一个缓存中的发布会更新另一个缓存。后台 I/O 继续留在创建它的 executor 上，预算本身不操作 socket。该组件尚未启用，普通命中不需要获取预算锁。

两个真实线程和本机 UDP DNS 对端的夹具已验证现有 `AddressCache` 与刷新组件：相同配置内的跨执行器同键去重、额度、token 失效后任务租约、不同配置复用视图编号的隔离、旧代取消排空和迟到响应。测试使用独立 epoll/io_uring executor；隔离 TSan/ASan/UBSan 通过，但预编译网络库未插桩。成员索引与这个生命周期仍需整合验证，该夹具本身不改变代理配置或启用后台刷新。

## 验证与决策

先固定 Xenium 版本并审查许可、编译器和项目第三方模块封装，再构建可重复的比较：当前每 worker 缓存、共享分片基线及 Xenium 候选采用相同的逻辑容量和答复；覆盖热键、均匀和偏斜键、不同 worker 数、命中/过期/替换/clear 混合及慢读者。统计常驻和峰值内存（含延迟回收和元数据）、上游请求数、吞吐、p50/p99/p999 与停止排空时间，明确机器、参数和运行次数。微基准不能替代真实代理流量。

功能测试须并发覆盖同键新旧答复、负答复、淘汰后旧刷新、clear/配置代次、不同 DNS 视图隔离、TTL 边界、刷新去重和全局限额、失败注入、停机及慢读者回收。使用线程竞争检测和长期压力验证；再以生产多 worker 独立 DNS 对端验证共享命中及取消。比较结果和完整语义通过后再决定实现与依赖，不应为了先接入乐观缓存而固化每 worker 的重复存储。
