# 规则集二进制格式设计

日期：2026-10-27。状态：KDL 2.0 与 BEVE 的有限谓词规则集及 v1 容器已实现，见[转换说明](../configuration/rule-sets.md)。跨版本兼容、扩展 schema、压缩、签名和性能基准仍待验证。

## 当前 v1 容器

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 8 | ASCII `NXRULES` 加一个零字节 |
| 8 | 2 | 容器版本，大端整数 `1` |
| 10 | 2 | 标志，大端整数 `0`；其他值拒绝 |
| 12 | 4 | BEVE payload 字节数，大端无符号整数 |
| 16 | 指定长度 | 单个 BEVE 对象，不允许前导分隔符或尾随数据 |

payload 对象必须恰好包含 `schema_version`（BEVE u32，值 `1`）、`kind`（字符串 `predicate`）和 `rules`（通用数组）。每个数组项是恰好包含字符串 `type`、`value` 的对象；字段顺序不重要，缺失、重复和未知字段均拒绝。当前只支持 `domain-suffix` 与 `ip-cidr`，没有压缩、摘要、索引或签名；全文件最多 1 MiB、数组最多 16,384 条、每个字符串最多 253 字节。BEVE 的长度采用该 Glaze 固定提交所实现的压缩整数编码。手工构造的 v1 样本用于检查字段与类型，库升级时仍须先验证兼容性。

## 已核对的 Glaze 来源

项目 recipe 固定 `glaze-kdl2.0-` 的 `feature/kdl2.0` 分支提交 `fc646588635c42cca142562d7b3d0484cc4493b7`（2026-10-27）；已核对相关格式文档和 BEVE 实现，验证当前规则集子集，但未验证完整 KDL 能力。

README 列出二进制格式 BEVE、CBOR、MessagePack、BSON、SQLite JSONB 和 EETF，并有对应头文件。下文区分格式适用性与 Nexus 性能判断，不将上游吞吐宣传作为项目实测。

## 格式选择

Nexus 自有规则集使用 **BEVE 作为 payload 编码**；外加最小、有版本的文件封装为当前设计草案。若未来重点变为第三方多语言直接生产/消费，可另行评估 CBOR，当前不同时发布两套正式二进制格式。KDL 与 BEVE 互转要求见[转换设计](../configuration/rule-sets.md)。

| 格式 | 本项目适用性判断 | 依据与限制 |
| --- | --- | --- |
| BEVE | 已确定的二进制方向 | 已有 Glaze 读写与 typed array 支持，可承载归一化规则/索引表；需要固定编码 profile 并验证跨版本 |
| CBOR | 对外交换优先候选 | IETF RFC 8949 标准，适合公开定义跨实现数据模型；类型映射、tag 和确定性编码仍需项目规定 |
| MessagePack | 已有生产者使用时可选 | Glaze 支持，无当前业务要求使其优先于前两者；不能假设任意 C++ 类型的映射都天然跨语言一致 |
| BSON | 当前不优先 | 未使用 MongoDB 文档生态；其文档与整数映射没有解决本项目特有问题 |
| SQLite JSONB | 当前不优先 | 适用于 SQLite JSONB 集成，本项目未选择 SQLite；不将它与其他数据库的同名 JSONB 混淆 |
| EETF | 当前不优先 | 未有 Erlang/Elixir 数据交换需求 |

格式能力依据来自上述本地分支文档；标准背景见 [BEVE 官方规范仓库](https://github.com/beve-org/beve)、[Glaze 二进制文档](https://stephenberry.github.io/glaze/binary/)与 [CBOR 文档](https://stephenberry.github.io/glaze/cbor/)。这些在线入口可能随上游变化，不能替代本地固定快照。

## 文件格式与执行模型分别设计

建议链路为：KDL 2.0 文本规则源 → 语义校验/规范化 → 类型化规则中间表示 → BEVE 打包 → 加载验证 → 不可变执行索引。反向从 BEVE 还原同一模型并写出规范化 KDL。主配置与规则集分别定义 schema；导入其他项目格式另行决定。

BEVE 是序列化编码，不是域名 trie、IP 区间集合或规则虚拟机。首版保留可逆的规范规则表示，加载时构建索引；若启动成本有证据表明需要优化，再增加可重建的编译索引区段。不得用不可逆优化结果取代反向转换所需的规则语义；不保存带指针的运行对象、C++ 布局或特定工具链产物。

大规模数据避免“每个域名重复一遍字段名”的对象列表，可用一个带名称的顶层对象加域名表、固定宽度整数数组、IP 地址/前缀表等明确区段。字符串/IP 的标准化、网络字节顺序与字段宽度由 schema 定义；typed array 不等于自动跨架构 mmap 结构体。

Glaze 的 lazy BEVE 支持借用视图、延迟遍历及可选索引，但缓冲必须存活；它不自动提供域名后缀/IP 匹配索引。首期以验证后构建自有不可变索引为基线，是否 mmap/借用加载单独测量寿命、对齐、端序和页错误成本。

## BEVE profile 与兼容性

外部 schema 使用固定字段名与显式、稳定的规则种类标识，不依赖成员声明顺序、C++ 类名、enum 默认反射名或 variant 下标作为长期协议。首版不默认启用 `structs_as_arrays`/untagged；若未来采用位置编码，仅用于明确版本化的固定记录。

所读分支 `docs/binary.md` 与 `include/glaze/beve/write.hpp` 已说明 BEVE v2 variant 写法变化；CBOR/MessagePack 文档也记录过 Glaze 类型映射的变更。因此“格式规范不变”不等于“升级库后任意 C++ 类型的输出不变”。固定 Glaze 提交、所用选项和映射规则，保留跨版本 golden 文件，不自动把库升级当成文件兼容。

BEVE 层负责语法解码，Nexus 层负责规则语义兼容。未知可选元数据可按约定跳过，但未知规则种类、动作、必要特征位必须拒绝，不能通过忽略字段把限制性规则变宽。

## 外层封装与发布

当前外层使用上面的最小布局，容器版本与 payload 中的规则版本分开。未来若加入必要能力位、压缩或摘要，须定义新版本及兼容行为，不能把规则版本与应用版本混为一谈。

压缩是独立选择。先比较未压缩 BEVE 与候选压缩方案的体积、加载 CPU 和峰值内存，再决定是否增加依赖；通用压缩不是 BEVE 内置保证。摘要用于检测内容变化/损坏，不能代替来源认证。若未来支持签名，明确覆盖哪些头字段与 payload 字节；固定实际发布字节可避免把未定义的序列化顺序误当作 canonical encoding。

远程更新先下载到受限临时存储，验证封装、解压限额、语法和语义并构建候选索引，全部成功后再发布；失败保留当前有效代次。远程内容与本机编译索引缓存分别标识，见[状态设计](state-and-cache.md)。

## 验收

使用实际域名、后缀、IPv4/IPv6 前缀和有序复合规则比较 BEVE、CBOR 与文本基线。分别测量文件体积、读取/解压、反序列化、索引构建、发布耗时、查询吞吐/尾延迟及峰值/常驻内存，不仅测序列化往返。

验证顺序/首命中语义、地址边界、字段缺失、未知类型、重复键、畸形长度、深度、尾随数据、压缩炸弹及旧版本文件。除了库的长度/深度保护，还要限制整文件、解压字节、规则数、字符串总量和索引编译工作量；解码成功不等于规则可安全发布。

未来加载加速或编译索引需证明与规范化规则结果一致，编译器/索引版本不匹配时可丢弃重建。当前没有证据可断言 BEVE 一定比 CBOR 更小或使匹配更快。
