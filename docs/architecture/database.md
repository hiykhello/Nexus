# 状态数据库设计

状态：设计，尚未实现或锁定依赖。数据库是可替换的持久状态服务，配置仍是 KDL；规则集格式仍为 KDL/BEVE，日志不写入状态数据库。语义及状态分类以[缓存与持久状态](state-and-cache.md)为准。

先以[持久化对象清单](persistence-inventory.md)确定业务需求。下面的 SQLite 和 BEVE 重放实验仅针对额外的跨重启安全假设，并不证明一般产品状态需要数据库；低频有界状态可先评估 BEVE 快照，是否需要数据库应由实际 FakeIP 和可选缓存负载决定。

## 用途与所有权

一个实例的状态 owner 拥有数据库和其稳定身份。首期候选按业务隔离为：持久状态（用户选择、后续 FakeIP 与网络恢复信息）和可丢弃缓存（DNS/规则缓存），可先用不同数据库文件以便单独清理和损坏隔离；没有对应功能时不预先创建表或假装存在数据。密码、密钥、token、TLS 会话秘密和日志不默认入库。FakeIP 的映射、地址预留与对外应答须遵守独立崩溃承诺，不能用异步缓存提交伪装成可恢复租约。

Linux 系统服务使用由服务管理器创建、属于运行身份的状态目录；用户进程由显式配置或平台用户状态目录决定，禁止写入源码目录。无路径时的具体用户模式目录解析、实例 ID、权限和只读模式须落到平台代码并测试；状态未启用时无需创建文件。数据库、WAL、共享内存、备份和稳定锁均位于受控目录，设置最小权限并检查符号链接、属主、实例碰撞与多进程访问。SQLite WAL 依赖同主机共享内存，不支持跨主机网络文件系统；不因路径看似本地就宣称已检测到全部不安全文件系统。[SQLite WAL](https://www.sqlite.org/wal.html)。

## 后端与异步边界

**SQLite 是首个待验证候选，不是已经选定或接入的依赖**。它提供本地事务与成熟工具，适合有版本的小型状态和批量缓存；需对锁定版本、许可证、构建、更新、跨平台、最小二进制和故障恢复做实际验证后决定。选择它不意味着 SQLite 内部文件 I/O 自动经过 Corosio/io_uring：常规 SQLite API 同步执行，专用数据库 owner/工作线程负责连接和事务，不在网络事件循环上调用；不未经验证自行改写 VFS、直接异步写数据库文件或绕过数据库锁。可丢弃缓存的后端与必要状态可独立禁用或替换。

隔离探针 `uv run python experiments/sqlite-replay/probe.py` 在 Python 自带 SQLite 3.53.1、WAL 和 `synchronous=FULL` 下验证：杀死提交前进程保留旧快照和水位，杀死提交后进程恢复新快照和水位；跨进程写事务竞争返回 `SQLITE_BUSY`，回滚不改变状态。本次 `/tmp` 为 tmpfs，100 次提交耗时约 1 ms，不代表磁盘性能；进程 kill 不模拟断电，事务锁也不提供整个密钥 owner 生命周期的排他或防回滚。

额外实验目标 `nexus-sqlite-replay-experiment` 将实际 C++ UDP 会话回调连接至系统 SQLite 3.54.0，使用 `uv run python experiments/sqlite-replay/session_probe.py <目标路径>` 验证两个会话共享全局水位、重新打开后各自拒绝已接受报文、跳过已预留响应 ID，以及事务中途注入回滚后两个快照和水位不变。夹具以事务写入单个会话和全局墙钟水位，水位采用固定长度大端 BLOB 支持完整无符号 64 位范围，ID 耗尽单独编码；测试覆盖最大值、递减和重复预留拒绝、耗尽恢复。它没有状态真实性和防回滚检查，也不是完整生产存储格式或后端，尚未接入服务或生命周期锁。

同一探针在真实会话接收及响应 ID 预留回调中暂停子进程并发送 SIGKILL：接收提交前恢复为空状态并允许首次接收，提交成功但回调尚未返回时恢复已提交窗口并拒绝重放；ID 预留提交前恢复原水位，提交后恢复则跳过整个预留区间。另模拟 ID 提交成功但回调报告失败，验证无响应且恢复跳过预留区间。这些仅覆盖单会话的指定进程崩溃点与单一不明结果，运行于 tmpfs；不模拟断电、其他存储故障或正式网络副作用。

Linux 生命周期锁实验位于 `experiments/state-owner`：私有目录内的稳定锁文件使用非阻塞 `flock`，描述符存活期间保持锁；检查目录和文件的属主、权限、最终符号链接及文件硬链接数。GCC 16.2.1、tmpfs 下通过独立进程竞争、SIGKILL 后接替和路径拒绝测试。SQLite 会话夹具已组合该锁，在数据库空闲时验证第二个进程在打开数据库前被拒绝，持有进程被杀后可以接替。探针还验证了锁文件被删除并重建后两个进程可同时获得不同 inode 的锁，因此目录和锁文件在 owner 生命周期内必须保持稳定，同一用户有权替换文件时这一假设无法由该锁保证。数据库路径别名、路径中间分量、网络文件系统语义、跨主机协调及备份回滚均未由此解决；实验尚未接入正式服务。

BEVE 是项目已有的序列化格式候选，适合配置、规则和可整体读写的状态快照；它本身不提供事务、并发锁、持久提交或崩溃恢复。对于每包更新的重放状态，若选用 BEVE 文件，仍需设计并验证增量日志或快照替换、同步顺序、崩溃恢复、资源界限、版本迁移和独占机制；具体读写放大与延迟应实测。BEVE 数据也可存于事务后端内。SQLite 尚未选定，后续应对实际工作负载比较两种方案，不能将格式和存储提交机制混为一谈。

非默认目标 `nexus-beve-snapshot-experiment` 使用现有 Glaze 模块编码最多 16 个重放窗口、时间水位和响应 ID 预留，并以同目录临时文件写入、文件 `fsync`、重命名、目录 `fsync` 提交；本机 owner 锁保护整个实验。`uv run python experiments/beve-state/probe.py <目标路径>` 在 GCC 16、tmpfs 下验证真实会话回调的两会话恢复和 ID 区间跳过，并对真实接收提交、响应 ID 预留及合成快照在重命名前、重命名后及目录同步后注入 SIGKILL：恢复分别保留旧状态或新状态，真实会话验证首次接收或重放拒绝、原水位分配或跳过新预留区间。还模拟 ID 快照写入成功但报告失败，验证不产生响应并在恢复时跳过区间；残留临时文件可在后续写入时清理。限定 BEVE 结构检查拒绝未知、缺失及重复字段、错误类型和长度，测试覆盖顶层和会话字段重复及截断。

实验快照加有 HMAC-SHA256 封装，解析前验证。夹具从调用方准备的 32 字节认证主密钥、16 字节实例标识及 16 或 32 字节代理密钥派生认证密钥，并将代理密钥长度纳入派生上下文；检查文件属主、权限、长度、最终符号链接及硬链接。两种代理密钥长度均通过真实会话及崩溃实验，跨密钥、跨实例及相同前缀跨长度复制被拒，样本快照中未发现明文密钥。测试密钥为公开固定值，文件位于实验目录内；该构造尚未完成审查，真实密钥生成、保护、备份、轮换和生命周期管理尚未设计。有效旧快照仍能通过 MAC，防回滚另需可信机制。实验每次提交重写整份快照，断电、实际存储写放大和性能仍未验证，也未接入正式服务。

夹具还模拟临时文件部分写入、文件同步前失败、重命名前失败和重命名后目录同步前失败：真实接收及响应 ID 回调均停止交付、令 owner 持续关闭；后续恢复按当前可见旧或新快照处理。此注入通过夹具分支实现，并非内核返回 EIO 或实际磁盘满；重命名后的可见状态也不能推断断电后的持久结果。

初步同步提交对比可用 `experiments/beve-state/compare.py <BEVE目标> <SQLite目标> <临时目录父路径>` 重现：各初始化 16 条会话后依次更新 200 次，测试实际快照替换或 SQLite WAL/FULL 事务。在本机 `/var/tmp` Btrfs 的一次样本中，BEVE 快照 p50/p95/max 为 958/1140/5542 微秒，SQLite 为 580/670/1537 微秒；`/tmp` tmpfs 样本分别为 9/9/15 与 10/12/35 微秒。BEVE 路径包含整份编码、HMAC、文件及目录同步，SQLite 夹具没有等价 MAC；本数据不是等安全语义的公平基准，也不覆盖并发、不同会话数量、冷热缓存、实际设备掉电或长期负载，不能据此确定后端。

一个连接由单一 owner 串行操作，跨线程用拥有型消息和有界队列；查询结果复制到调用方可安全拥有的数据，事务结束后不暴露借用视图。限制待处理请求、每项和批次字节、存储总量、读取时间和重试；队列满时缓存可丢弃并计数，权威状态返回可区分的资源错误或按明确期限背压。操作取消仅取消等待或请求中止，不推断已开始的提交已撤销；回执必须区分未提交、已提交和结果不确定，必要时使用请求 ID/revision 去重。

## 事务、恢复与迁移

版本化 schema 和显式迁移顺序。启动先取得实例所有权，再检查版本、目录和完整性，迁移在事务中执行；未知新版本或迁移失败明确拒绝启动，不自动清库。缓存损坏可按显式策略隔离重建；用户状态和 FakeIP 损坏不得静默删除，需备份、诊断和恢复路径。离线备份使用数据库支持的一致性机制，不仅复制正在写入的主文件；恢复和 WAL/SHM 生命周期需演练。

候选 WAL 模式允许读写并发但同一数据库仍只有一个 writer；长读事务可能阻碍 checkpoint，使 WAL 增长。限制读事务寿命，测量 WAL 高水位、checkpoint 延迟和忙锁处理，不假定删除 WAL 可安全释放空间。[SQLite WAL](https://www.sqlite.org/wal.html)。持久状态候选 `synchronous=FULL`，缓存可考虑 `NORMAL` 并明确掉电时最近提交可丢失；具体保证仍依赖 SQLite、系统调用、文件系统和设备，须以故障注入验证。[SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)。不能将数据库 commit 与真实 nftables、路由等外部操作描述为跨系统原子事务；需意图记录、执行和重启核对。

每个操作区分接受、读取可见、事务提交和持久性确认；持久配置覆盖在提交成功后才对外发布，失败时旧代继续生效。缓存可异步合并，TTL、视图、版本、清空屏障和 FakeIP 所有权由业务层校验。停止先关入口，按可报告期限排空/失败并关闭连接和锁；数据库阻塞调用不一定可及时取消，超过期限时报告明确状态，不能让析构伪造提交成功。

## 验收

针对固定后端和构建执行：迁移前后与降级、空库、只读、磁盘满、IO 错、事务回滚、锁冲突、并发读写、停机超时、WAL 增长/checkpoint、崩溃重启、备份恢复、损坏隔离、多实例和路径权限。验证掉电保证需真实平台/文件系统测试或有界故障模型，普通进程 kill 不等于断电。测量执行线程、排队延迟、缓存写放大与大小上限，检查敏感数据和清理边界；在业务接入前不宣称持久恢复功能可用。
